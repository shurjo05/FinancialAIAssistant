# Security Overview & Threat Model

A concise, honest description of how JoMoney protects user data, what it
deliberately does *not* do (and why), and how known risks are mitigated. This is
a personal-finance app, so the primary assets are **user financial data** and
**account access**.

## Authentication & session management
- **Passwords** are hashed with **bcrypt** (per-password salt), never stored or
  logged in plaintext, and never returned by the API. Login returns a generic
  "Incorrect email or password" (no user enumeration on the login path).
- **Sessions** use stateless **JWT** (HS256), `sub` = user id, 24h expiry.
- **Revocation:** each user has a `token_version`; tokens carry a `ver` claim and
  are rejected once it no longer matches. **"Log out all devices"** and
  **changing your password** bump the version, so every outstanding token —
  including a stolen one — is invalidated immediately. This closes the
  otherwise-24h window where a compromised token could not be cut off.

## Authorization & data isolation
- Every data endpoint requires a valid token (`get_current_user`).
- **Per-user isolation:** every query filters by `user_id`; single-row access
  checks ownership and returns **404** (not 403) for another user's row, so it
  doesn't leak existence. The **LLM's tools are bound to the caller's `user_id`**,
  so the model itself cannot reach another account's data.
- This is enforced in application code and **verified by cross-user isolation
  tests**.

## Secrets & transport
- `JWT_SECRET`, `DATABASE_URL` (Neon), and `GOOGLE_API_KEY` are **environment-only**,
  backend-only, never in git or the frontend bundle. `.env` is gitignored.
- Production **fails to boot** if `JWT_SECRET` is still the dev default.
- **No secrets in logs** — logs carry request metadata (path/status/latency), not
  payloads; a redaction filter scrubs bearer tokens / secret-named fields as
  defense-in-depth.
- All traffic is **HTTPS** (Render-terminated TLS).

## Input validation
- **CSV upload** is parsed, never executed. Guardrails: **5 MB** size cap
  (bounded read), **10,000-row** cap, empty-file rejection, `.csv`-only.
- **CSV formula injection** (`=`, `+`, `-`, `@` cells) is not a live risk here —
  values are rendered in React (auto-escaped), not in Excel. It would matter only
  if we added CSV *export*, which we don't.

## LLM tool-calling
- Prompt-injection via merchant text is **bounded by design**: the model can only
  call **deterministic, typed-argument, read-only, user-scoped** tools. It cannot
  execute arbitrary SQL, write data, or cross accounts. Numeric answers are
  computed by the tools, not generated by the model.
- The tool loop is bounded (`maximum_remote_calls`), and failures fall back to a
  deterministic engine.

## Abuse & rate limiting
- **Per-IP** limits on `/login` and `/register` (brute-force / enumeration
  defense); **per-user** limit on `/api/query` (protects the LLM budget from a
  single account). In-memory limiter (single instance; Redis intentionally
  avoided at this scale).

## Dependency management
- **Dependabot** opens weekly update PRs (pip, npm, github-actions).
- CI runs **`pip-audit`** (backend) and **`npm audit --audit-level=high`**
  (frontend); a known vuln fails the build.
- **Triaged advisory:** `PYSEC-2026-1325` (ecdsa timing side-channel, transitive
  via `python-jose`, no fix released) is ignored in `pip-audit` because we sign
  with **HS256** — the ECDSA code path is never used. Migrating `python-jose` →
  `PyJWT` would drop the dependency entirely (a possible future cleanup).

## Considered and deliberately deferred (with rationale)
- **Postgres Row-Level Security (RLS):** would add a DB-level backstop against a
  *future forgotten `user_id` filter*. Deferred because our app-level isolation
  is comprehensive and tested, and RLS here is Postgres-only (breaks the
  SQLite/local-test symmetry) and requires per-request session-variable plumbing
  with a real "silently no-ops if misconfigured" footgun.
- **Per-device session registry** (revoke one device, list active sessions):
  deferred in favor of the lighter `token_version` (revoke-all), which covers the
  security-critical case (kill a compromised session now).
- **Email verification / full register anti-enumeration:** without a
  verification flow you can't fully hide whether an email is registered; we
  rate-limit `/register` to prevent bulk harvesting and note the residual.
- **Refresh-token rotation, RBAC/roles, 2FA, WAF, secrets-vault:** out of scope
  for a single-tenant portfolio app at this scale.
